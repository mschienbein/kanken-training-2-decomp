# Independent harness-oracle review

## Verdict: FAIL — harness oracle ready to start decompiling

**Reviewer:** ReviewHarnessOracle. **Runtime-reported family/model:** OpenAI / `openai-codex/gpt-6.1-sol`.

This is a scoped review of `tools/{inplace,match,build,rom,ctrfmt,denominator}.py`, `ci/progress_report.py`, their tests, and the necessary image/toolchain/catalogue interfaces. It is not an analyzer-heuristic review or a review/adoption of the pilot source. The governing README, AGENTS, ACCEPTANCE and STATUS were read first. No other review was read before this verdict was written. All reviewer-created files, imports, copied harnesses and experiments are under `scratch/review/`; canonical files, accepted receipts, Git and `boot9.bin` were not changed or accessed for mutation. No `boot9.bin` was read.

The existing suite passes, and the pinned plaintext dump imports correctly. Nevertheless, two real-compiler reproductions produce **false PASS** results. In the strongest case the catalogue is structurally valid, non-overlapping and hash-chained: the linker places two distinct initialized writable C objects at the same address, and both MATCH and the full build PASS. The verdict does not depend on the already-open compiler/pilot gates.

### F11 — minor: additional ABI edge observed

`tools/inplace.py:297-306` permits **R_ARM_JUMP24 on an unconditional BL** to change directly to BLX when the target is Thumb. AAELF32 reserves that conversion for R_ARM_CALL; JUMP24 must use an interworking veneer. `elf-edge-results.json:jump24_bl_to_thumb` shows the unexpected BLX encoding. Current ARMCC fixture output uses CALL for unconditional BL and JUMP24 for a tail B, so this is not evidence of an affected current game function. The minimal repair is to gate direct interworking by relocation type as well as opcode, keeping PC24's supported historical behavior explicitly distinguished. Treat this as an additional strict-relocation qualification alongside F03/F05, not as a request to silently generate veneers.

## Coverage conclusions and inherited qualifications

- **Credited-byte coverage:** with a valid disjoint catalogue, the current exact-length check causes each selected section to overwrite its full credited range; I did not find an ordinary suffix-left-original escape. Uncredited executable sections are not written outside a unit's declared credit. F02 is the concrete escape: overlap plus final-image-only verification can conceal the wrong object bytes. F01 is independent of catalogue overlap.
- **Input identity:** a fixed wrong CCI cannot pass the complete-file SHA-256 check absent changing the trusted pins or a hash collision. Exheader, ExeFS header and each ExeFS payload are hashed on import; the plaintext path is correct for the supplied dump. RomFS verification in `rom.py:113-118` checks the master hash region, not every lower IVFC level, and the configured raw RomFS pin is not consumed by `import_rom`. The up-front whole-CCI pin covers that gap for the immutable supplied file; I did not demonstrate a wrong-dump acceptance. This is not described as full IVFC-chain traversal.
- **BSS bounds:** actual `Image.bss` is `[0x243908, 0x4e32ec)`, from data address plus **unrounded** data size `0xC908`, then BSS `0x29F9E4`. Using `mapped_size=0xD000` as the BSS start is not supported by the 3DS loader's allocation formula. Luma's loader uses `ceil((data.size+bss_size)/4096)` for total RW pages; page padding is not another BSS-sized displacement. No BSS-start off-by-page finding is asserted. Bounds alone still do not prevent F01's conflicting allocations.
- **Progress is not an acceptance certificate:** unknown addresses are refused and duplicate names do not inflate the set. However, a human-managed `matches.json` is the numerator authority; no accepted receipt or source existence is checked. A synthetic missing-source/nonexistent-profile unit receives 100% progress with a valid denominator chain (`build-credit-probes/results.json:unbacked_report_measures`, `followup-results.json:alias_history_verify`). This is a trust-boundary qualification of the current design, not a claim that the empty canonical accepted ledger is already fraudulent. The actual current accepted count remains zero. The hash chain detects unrecorded catalogue drift; it does not authenticate a reviewer or make self-declared credit accepted.
- **Hybrid scope:** data ordering, bytes outside credited functions, veneers, unplaced allocated metadata, global linker selection and a full original-armlink image are not proved by these receipts (`tools/build.py:12-13`, `docs/RESUME.md:64-68`). A zero-unit original-copy/recompression receipt is not itself the per-function/per-data split-and-relink proof required by H3. The historical H3 claim should retain that distinction. F01 goes beyond uncertain data ordering: two distinct writable C objects cannot legally become one storage object.
- **Receipt reproducibility:** existing receipts bind the listed `.c` files, objects, compiler executable, profile/lock/names/catalogue/matches and outputs. They do not bind the exheader, transitive included headers or harness implementation. No claim of a complete source/dependency/tool snapshot is made by this review's successful receipt hash checks.
- **Open gates remain open:** STATUS reports H5 partial, H7 candidate-only, H8 a registration stub, H11 open, and no accepted pilot. The profile is not frozen across the required stratified features. The successful existing receipt checks do not promote any candidate, satisfy two fresh accepted builds, or close those gates. The 39,470 unknown text bytes and 350 catalogue anomalies remain inherited, not silently waived or re-investigated here.
- **Windows:** no native Windows execution was available/performed. Source uses `Path`, subprocess argument lists and explicit UTF-8/LF for hash-bearing JSON, and bypasses wibo on Windows. No deterministic Windows path failure was established in the reviewed target. **[INFERENCE]** `toolchain.py:83` still depends on host/default subprocess text decoding; `LC_ALL=C` alone is not a native-Windows encoding contract for diagnostics containing non-ASCII paths. Native ARMCC/locale behavior and cross-host catalogue/object/build determinism remain unverified, as the resume document already requires. No emulated locale result is misrepresented as a Windows run.

## ABI / platform references

- [Arm AAELF32](https://github.com/ARM-software/abi-aa/blob/main/aaelf32/aaelf32.rst), release 2025Q4 as retrieved: static relocation table; static-data overflow table; Arm call/jump relocations; Thumb call/jump relocations; static miscellaneous relocations (V4BX's symbol may be null). In particular PREL31 is `((S+A)|T)-P`, ARM BL/BLX REL addends use `sign_extend(insn[23:0]<<2)`, and JUMP24 interworking needs a veneer. The original BLX H bit is not mistakenly counted as an addend in this review.
- [Luma3DS loader.c](https://github.com/LumaTeam/Luma3DS/blob/master/sysmodules/loader/source/loader.c), `LoadProcessImpl`: RW page accounting uses raw initialized-data size plus BSS size; initialized data pages are separately rounded.
